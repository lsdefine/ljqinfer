# Decode 开发计划与执行约束

## 目标与基线
- 目标仓：`/data/ljqinfer_dsv41f_tp8`，prefill 基线提交：`8cdca784`。
- 参考仓：`S:/ljqinfer_dsv41f_tp8`（node09 同名引擎）。
- 最小执行单元 B1Q6，支持 B1Q6～B4Q6；B8 通过集中容量常量调整、重新预分配和捕图扩展，不重写算法路径。扩容前必须重算显存预算。
- B1Q6 稳态完整 decode 轮分三档：简单目标 <40ms、普通目标 34ms、困难目标 25ms。本轮先完成简单目标，40ms 不是最终目标。计时包含：包含 Engram 准备、target verify、接受判定/提交、draft 与必要同步；不以单图耗时或除以 Q 后的数字替代。
- prefill 已阶段性可用，本轮不重开短输入跨桶差异排查；保留现有缓存恢复与 replay128 语义。

## 不可违反的三条规则
1. 代码与文件简短清晰，按职责组织；优先修改已有文件，仅增加独立 decode 必需模块，不向仓内堆积实验脚本或重复报告。
2. 生产执行路径唯一且显式。decode 算子与 prefill 分开，允许代码重复；禁止运行时通过 is_decode、shape 猜测、环境变量或隐藏 fallback 切换算法。参考计算只用于独立测试。
3. 计算资源预先声明、预分配。启动分配全部设备 tensor、workspace、KV/页表池、图资源及固定 host staging；运行只填充/复用，不扩容、不临时创建设备张量、不 lazy build/capture。请求队列等外围对象与设备计算存储分开管理，不把设备分配藏进调度层。

## 架构与图捕获
- server 管协议，strategy 管调度，model 管执行与状态，ops 管计算；非 NPU/算子相关机制尽量直接沿用 node09，不另造外围框架。
- 集中声明 Q=6、MAX_BATCH=4、slot/context/page 容量；不得散落 B4 或 B8 特判。
- 启动预热并捕获 B=1、2、3、4 四档图组。参考实现每档含 verify 图和 draft 图，中间执行接受判定与提交；不是声称总计只有四个底层 graph 对象。
- token、slot row-map、位置、页映射、接受数等动态值进入持久 buffer；图冻结的地址与 storage 不重绑。
- 计算及通信必须真实参与图回放。裸 HCCL/原生核使用调用时正确的 stream；多流依赖明确，图长期持有 buffer、stream、event 及必要闭包。
- 相互排斥的图可按生命周期复用 workspace，但不得覆盖仍被其他图/请求读取的状态；Engram host staging 按实际消费者生命周期隔离。
- Past 是已消费前缀的唯一真相；verify 写投机区域，接受后才提交，拒绝部分不得污染正式 KV/carry。decode 必须接续 prefill 和 cold restore + replay128 的状态。
- 动态上下车在轮次边界进行，保留 node09 的 admit / roll / dismiss、BOARD_EVERY、EOS/取消、日志及缓存语义。初版不增加异步 prefill 路径；上车 prefill 对在车请求的暂停要如实统计。

## 执行顺序与完成标准
### 1. 固定接口与资源预算
- 盘点现有 NativeDecode、独立 native 核及其可复用绑定；保留有用实现，不维持新旧双生产路径。
- 列出输入/输出/读写契约，以及权重、prefill 常驻计划、decode 四档图、draft、KV 池、页表、通信、host staging 的共驻预算。
- 页号更新复用预分配暂存区，去掉更新映射时临时 torch.tensor 的设备分配。
- 完成标准：资源所有者与释放顺序清楚，容量不足在启动/准入时显式拒绝，不运行中扩容兜底。

### 2. 独立算子与 B1Q6 闭环
- 补齐 decode 专用线性层、attention、Engram、MoE、归约、head，以及 DSpark 所需计算。
- 按 node09 状态契约接通 draft → verify → 接受判定 → commit，尽早跑通真权重 B1Q6 图回放和真实生成。
- 完成标准：数值与接受/拒绝语义可信，未接受 KV 不泄漏，prefill/冷恢复状态可直接衔接；不拿局部算子成功冒充完整引擎。

### 3. 扩展四档预捕获
- 启动一次性构建 B1～B4 的全部图组与固定输入输出，运行只根据批宽选择已建图。
- 完成标准：四档重复回放及切换正确，通信确实回放，无在线捕图、隐式 eager 路径或设备动态分配。

### 4. 动态上下车接入
- 复用 node09 外围策略，以 row→slot 映射隔离批行与请求状态。
- 覆盖 1→4→2→1、非连续 slot、slot 复用、EOS/取消、跨页及长上下文，核验所有 TP rank 同步状态。
- 完成标准：请求不串 token/KV，释放与复用安全，日志保留完整阶段口径。

### 5. 达标、提交与交付
- 先获得完整 B1Q6 基线，再按实测主瓶颈优化，不先搭庞大框架或长期泛化验收。
- 测试声明上下文长度、容量、预热轮数、样本数；报告完整轮平均/P95、分阶段时间、接受数和有效输出 TPS，长上下文单列，不能用短上下文结果泛称全部达标。
- 本轮先交付 B1Q6 完整轮 <40ms 的可用版本；34ms、25ms 为后续普通/困难优化目标，不阻塞首阶段交付。B2～B4 报告实际延迟与吞吐，不预造指标。
- 检查 steady-state 分配、页边界、上下车及显存高水位；数值/状态门槛与性能门槛分别记录。
- 已验证的合理改动及时提交；不得同时启动两套 TP8。失败先读错误与现场，不无信息重复试验。

## 成功推进即提交，提交说明用于选择回退点
- 每次取得可验证的成功推进，完成最小对应验证后立即 commit，不积攒大批未提交改动；失败实验不作为成功成果提交。
- commit message 是版本状态与回退索引，不是为了证明什么：引擎出问题时，仅看提交说明就应能选择已知可用版本，不必重跑历史实验判断回退到哪里。
- 实现提交写清该版本可用功能与配置范围、实测正确性/性能/内存结果及计时口径、相对上一可用点的变化、已知问题与未测项、上一相关可用提交 hash。局部里程碑标明不是完整引擎可用点；叶算子收益不能冒充整轮收益。
- 写明回退依赖、ABI/配置/已编译库兼容要求及是否需要重编译或重启，避免只退源码却加载新库。关键结果直接写在 message 中；复现命令及日志位置仅作补充，不要求翻日志才能判断版本状态。
- 仅记录实际执行的实验；文档改动标明仅做文档检查，不虚构设备验证。

## 模块与任务必须可独立交付
- 解耦不是仅拆文件：子任务应能交给不掌握整套实现的人，依靠契约和独立台架完成及验收，无需修改无关模块。
- 子任务开工前明确目标/非目标、输入输出 shape/dtype/layout、状态读写与资源所有权、stream/通信/捕图约束、允许修改的文件、依赖和验收标准。
- 接口先定；构建层显式分配并传入资源，禁止隐藏全局可变状态、跨模块私有字段依赖和隐式分配。公共接口变更先协调。
- 子任务可用固定输入或独立参考替代依赖进行测试，但替代物不进入生产形成 fallback；独立通过后仍需集成验证。
- 初始任务边界：decode叶算子（按算子族）、Past投机写入与提交、DSpark draft、图资源与捕获执行、动态批调度。各自交付契约、实现、可复现测试及证据，由集成方组合B1Q6闭环，不各自复制整套引擎。
- 使用最小必要接口，不为解耦增加通用框架、无用抽象或碎片文件。可外包不等于允许多套TP8并跑，设备实验仍串行调度。
